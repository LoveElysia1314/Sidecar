# Dualign 工作报告架构

状态：当前实现  
更新日期：2026-08-24

## 产品边界

Dualign 一次处理两份平行文档。文档 A / 文档 B 是中性位置，不隐含“权威原文”和“附属译文”。如果同一作品有三种语言，应按实际需要建立多个独立文档对；系统不通过第三种语言推导传递关系。

Dualign 负责对齐、规则校订、AI 建议、人工审核和显式固化修改。作品目录、抓取、翻译任务、部署和阅读器页面由上层应用负责。

## 唯一持久工作状态

每个文档对由三个文件组成：

```text
document-a.md
document-b.md
chapter.report.json
```

`report.json` 是唯一的对齐与校订状态，包含：

- 两份源文档的规范化 SHA-256；
- 对齐模型、算法和非敏感配置来源；
- 带稳定关系 ID 的不可变初始关系 `ops`；
- 只以稳定关系 ID 持久化身份的 `repair_log`；
- AI 建议、人工审核状态、评分和固化历史。

报告不复制完整正文。每条 `ops` 关系保存 `id/s/t/sc`；旧报告缺少 `id` 时按原顺序派生兼容 ID。新报告中的修复动作只持久化 `relation_ids`；`op_index/operation_indices/data.orig_snaps` 只在读取旧报告时用于恢复身份，写回时删除。运行期 `operation_indices` 是由当前关系顺序派生的临时投影。回放层使用 `RelationGroup(relation_id, ordinal, rows)`：ID 是身份，ordinal 只是当前快照地址。`RepairState` 总是从原始关系重放操作，因此编辑、撤销和重新编辑不会造成后续关系身份漂移。源文档哈希或模型配置不匹配时，报告失效并要求重新对齐。

旧报告不迁移：发现没有 `format: dualign-report` 的文件时直接提示重新对齐。嵌入向量 SQLite 缓存独立保留，可以显著降低重新生成报告的成本。

报告序列化只由 `report_io` 负责。运行期 `AlignmentSnapshot/RepairState` 不提供另一套
`to_dict/from_dict` 快照格式，避免内部撤销状态和正式报告演变成两个可持久化权威来源。

“snap”不再是关系、表格或 AI 工具的领域概念。持久身份统一称 `relation_id`，当前顺序统一称
`ordinal`，界面和 Agent 均显示“关系 N”。`AlignmentSnapshot` 只表示对齐完成时不可变的正文与
关系基线；底部面板的 snap point 只表示物理吸附档位。旧报告中的 `orig_snaps`、旧评分键和旧
Agent 参数名仅在各自读取边界接受，进入运行状态后立即投影成关系身份或序号。

## 算法包边界

`dualign.algorithms.mdl` 是生产求解器；`dualign.core.aligner` 只负责正式结果契约与统计门控，
不再导入、适配或导出 legacy 算法。冻结的 `legacy_anchor_aligner` 仅由显式
`legacy-anchor-v1` CLI/benchmark 分支惰性加载，
不会作为 MDL 拒绝后的回退，也不再向 `dualign.core` 公开锚点阈值、归一化或候选内部函数。
生产与归档算法共用的关系类型标签和文本拼接位于 `dualign.core.text`，因此生产运行期不依赖
legacy 实现细节。
`LegacyAnchorConfig` 和旧质量诊断也不从 `dualign.core` / `dualign.services` 聚合 API 导出；需要
回归旧算法的代码必须显式导入归档模块；正式 `AlignConfig` 不再含算法选择字段，`align()`
传入其他配置类型会直接报错。

## 保存与固化

- 自动保存和“保存工作报告”只原子更新 JSON，不改写源文档。
- 未选择“固化修改”时，磁盘上的两份 Markdown 始终保持原样。
- 固化范围包含文档 A/B 的合并、拆分、文本校订六类，以及双侧“删除文本对”，可以使用预设或逐项选择；占位仅是工作报告中的显示/补缺操作，不写入正文。
- 同时改变 A/B 结构的 N:M 合并或拆分按原子操作处理：必须同时启用两侧对应类型，否则整个操作保留在当前报告中。
- 固化前展示两侧差异，再以可恢复的三文件事务写入文档 A、文档 B 和更新后的报告。
- 已固化效果进入新正文与新 `ops` 基线，并从当前 `repair_log` 消失；未固化操作会按稳定关系身份保留，同时生成兼容的位置投影。
- 重对齐后，两侧内容完全相同且在新旧关系中均唯一的关系继承旧 ID；改变边界或内容的关系获得从未使用的新 ID，不能仅凭新位置继承身份。
- 固化前的完整操作及实际应用范围归档到 `history`。AI 建议按关系 ID 分组；已处理或目标已变化的建议会清理，未受影响的待处理建议直接继承最终关系 ID。持久评分以 `(relation_id, sub)` 为内存键并按关系 ID 嵌套写入报告；旧 `snap_sub` 键只在载入边界转换一次。完整固化且已有当前评分的关系会把该评分提升为新基线；部分固化则失效重算。
- `flag` 与 `ok` 不改写正文：目标关系仍存在时会重锚保留；删除固化使关系消失时，它们仍可从 `history` 中完整追溯。
- 备份职责由 Git、文件历史或调用方承担，Dualign 不再生成 `.bak`。

## 阅读器兼容制品

逐行阅读器仍可消费等长的两份 Markdown，但它们不是数据源。构建时调用 `materialize_reader_rows()`，从源文档和报告在临时目录中重放并生成，构建完成立即删除。这样既保留现有阅读器兼容性，也避免长期维护 `repaired/` 副本。

## 明确移除的概念

- 不再隐式导出修订后的 Markdown；
- 不再维护 `repaired/`、`.bak` 或文件置换式“晋升”流程；
- 不用 YAML 复制 JSON 工作状态；
- 不提供旧报告格式迁移；
- 不把恢复文件与正式对齐数据拆成两套相互同步的权威状态。

## 数据流

```text
文档 A + 文档 B
       │
       ├── 对齐 ──> report.json
       │                 │
       │          校订 / AI / 人工审核
       │                 │
       │          原子保存 report.json
       │                 │
       ├── 按类型固化 <────┘
       │
       └── 阅读器构建：临时物化等行 Markdown ──> 静态站点
```
