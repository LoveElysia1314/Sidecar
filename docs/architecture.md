# Dualign 工作报告架构

状态：当前实现\
更新日期：2026-08-25

## 产品边界

Dualign 一次处理两份平行文档。文档 A / 文档 B 是中性位置，不隐含“权威原文”和“附属译文”。如果同一作品有三种语言，应按实际需要建立多个独立文档对；系统不通过第三种语言推导传递关系。

Dualign 负责对齐、规则校订、AI 建议、人工审核和显式固化修改。作品目录、抓取、翻译任务、部署和阅读器页面由上层应用负责。

## 唯一持久工作状态

每个文档对由三个文件组成：

```text
document-a.md
document-b.md
chapter.report.json
```

`report.json` 是唯一的对齐与校订状态，包含：

- 两份源文档的规范化 SHA-256；
- 对齐模型、算法和非敏感配置来源；
- 带稳定关系 ID 的不可变初始关系 `ops`；
- 只以稳定关系 ID 持久化身份的 `repair_log`；
- AI 建议、人工审核状态、评分和固化历史。

### 人工审阅完成语义

内容作者与审阅者是两个正交事实。`RepairAction.source` 记录方案来自 `auto / ai / user`；
`data.reviewed_by` 记录之后由谁审过。关系投影再把两者归纳为
`none → proposed → agent → user`：自动方案经 AI 通过后仍是 `source=auto`，只增加
`reviewed_by=[ai]`；人工方案经 AI 复查后仍保持 `source=user`。因此重新执行 AI 审阅时可以
只撤销 AI 审阅凭据，不必删除自动或人工内容成果。普通无异常的 1:1 关系可以一直保持
`none`，且不因此成为人工审阅工作。

`project_relation_statuses()` 是关系状态的唯一投影。一个仍存在的关系，只要具有初始
异常、当前异常、flag、修复动作或非 `none` 审批，就属于人工审阅范围；其中只有
`approval=user` 才关闭人工审阅要求。删除后的关系不再存在，因而不再要求审批。
`manual_review_counts()` 从同一投影派生章节级 `subjects / required / completed` 计数。
GUI 自动跳转和 Reader 的报告摘要都消费这套计数，不再比较历史字符串
`unreviewed`，也不从审批状态集合猜测整章是否完成。

整章 AI 审校只消费仍需处理且 `approval != user` 的关系。用户标记 OK 的异常关系，以及
没有异常但已经人工校订过的关系，都属于已经做出的人工决定，默认不再交给 AI 推翻；用户
显式点击“审校本条”时则以这次明确意图为准，可以重新送审。该差异是输入集合语义，不是
GUI 特判。

`ai_review.status` 的完成状态只有 `completed` 与无待审项时的 `skipped`。`partial` 表示
轮数用尽后仍有待审关系，`failed/error` 表示调用失败，`forced` 表示模型显式要求带未处理项
结束。报告还保存 reviewed/pending 计数与 ID、轮数、模型和提示词工具契约 SHA-256；这些
字段都是可从权威报告重建/审计的运行摘要，不能替代 `repair_log` 的关系级事实。

报告不复制完整正文。每条 `ops` 关系保存 `id/s/t/sc`，修复动作只持久化 `relation_ids`；`relation_identity` 另存每条关系两侧完整文本的 128 位内容指纹，不包含位置、评分、算法版本或关系 ID。运行期 `RepairAction` 也只含关系 ID；重放、GUI 和固化需要位置时，统一经 `AlignmentSnapshot.operation_indices()` 即时投影。回放层使用 `RelationGroup(relation_id, ordinal, rows)`：ID 是身份，ordinal 只是当前快照地址。`RepairState` 总是从原始关系重放操作，因此编辑、撤销和重新编辑不会造成后续关系身份漂移。

正文哈希或对齐算法语义身份不匹配时，只表示旧的**对齐缓存**不能直接使用，并不等于所有校订状态失效。重新对齐后，统一协调器按两侧完整文本指纹迁移关系 ID、修复动作、AI 建议与评分：正文完全相同时，相同关系拓扑可安全消歧重复文本；正文变化时，只复用新旧快照中均唯一出现的精确关系。未映射关系和内容已变化关系局部失效，新关系获得新 ID。每次协调结果写入 `history` 供审计。

格式迁移仍从严处理：只有 `format: dualign-report/v1` 满足当前持久化契约；未版本化或其他版本的文件一律失效并重新对齐。缺少 `relation_identity` 的早期 v1 报告在正文哈希仍相同时可由现有行安全计算一次指纹；正文已经变化时不猜测旧内容。嵌入向量 SQLite 缓存独立保留，可以显著降低重新生成报告的成本。

### 拒绝结果的 GUI 能力

`rejected` 报告没有可靠的关系投影，因此自动修复、AI 校订、人工关系校订和固化均禁用。
拒绝不代表两份 Markdown 不可阅读：GUI 仍加载原始行并进入逐行预览，保留“预览”按钮，
只禁用“校订”模式。缓存命中与新计算必须走相同的预览语义；恢复已有拒绝报告时只读取
报告，不因打开文件而重写它。

生产流程不再判定文档平行性。空输入、输入规模超过安全处理范围，或原子对齐超过固定的
60 秒时会产生 `rejected`；这些都是运行条件，不是内容质量结论。其余结果由组合证据决定
`aligned / needs_review`，其中 `needs_review` 仍有可消费的暂定关系。报告只保存用户可理解
的结果原因与阶段耗时，不写入校准、工作量代理或内部状态机参数；任何拒绝均不得静默回退
legacy。

报告序列化只由 `report_io` 负责。运行期 `AlignmentSnapshot/RepairState` 不提供另一套
`to_dict/from_dict` 快照格式，避免内部撤销状态和正式报告演变成两个可持久化权威来源。

“snap”不再是关系、表格或 AI 工具的领域概念。持久身份统一称 `relation_id`，当前顺序统一称
`ordinal`，界面显示“关系 N”。`AlignmentSnapshot` 只表示对齐完成时不可变的正文与关系基线；
底部面板的 snap point 只表示物理吸附档位。

Agent 以 `review_region` 而非单个异常关系作为决策边界。区域输入同时给出初始文本、当前拟修复、
有界上下文、结构化证据和可精确预览的候选方案。供人和模型共用的自动标记在生成源头使用
中性事实表述，不由 Agent 层过滤；人工填写的说明作为证据原样保留。
生产工具面只保留 `inspect_region / accept_candidate / edit_region / delete_region /
defer_region / finish_review`。接受候选或编辑区域都是原子决定，最后编译回普通 `RepairAction`；
同时解除 `[F]` 时，标记证据作为主要动作的审计元数据，而不是另一条待选建议。因此报告、GUI
与固化流程无需维护第二套 AI 状态格式。旧关系工具仅保留为未公开的脚本兼容边界。

自动修复策略原样进入 AI 会话，并作为多个语义正确方案之间的修改偏好：`src/tgt` 分别保持
文档 A/B，`minimal` 选择信息完整前提下的最小结构变化。minimal 对 N:0 / 0:M 在缺失侧放置
占位符，不删除唯一存在的文本；因此普通自动校订、AI 前置拟修复和 GUI 共用同一矩阵，无需
AI 专用例外。最终由 `edit_region` 补写、确认冗余或延后。`[F]` 是否解除也由每次接受/编辑
显式决定，而不是由正文发生变化自动推断。

AI 运行过程的界面反馈采用语义事件而非原始模型输出；待实施方案见
[AI 审校运行可视化设计](ai-review-ux.md)。

## 算法包边界

`dualign.algorithms.mdl` 是生产求解器；`dualign.core.aligner` 只负责正式结果契约与安全边界，
不再导入、适配或导出 legacy 算法。冻结的 `legacy_anchor_aligner` 仅由显式
`legacy-anchor-v1` CLI/benchmark 分支惰性加载，
不会作为 MDL 拒绝后的回退，也不再向 `dualign.core` 公开锚点阈值、归一化或候选内部函数。
生产与归档算法共用的关系类型标签和文本拼接位于 `dualign.core.text`，因此生产运行期不依赖
legacy 实现细节。
`LegacyAnchorConfig` 和旧质量诊断也不从 `dualign.core` / `dualign.services` 聚合 API 导出；需要
回归旧算法的代码必须显式导入归档模块；正式 `AlignConfig` 不再含算法选择字段，`align()`
传入其他配置类型会直接报错。

## 保存与固化

- 自动保存和“保存工作报告”只原子更新 JSON，不改写源文档。
- 未选择“固化修改”时，磁盘上的两份 Markdown 始终保持原样。
- 固化范围包含文档 A/B 的合并、拆分、文本校订六类，以及双侧“删除文本对”，可以使用预设或逐项选择；占位仅是工作报告中的显示/补缺操作，不写入正文。
- 同时改变 A/B 结构的 N:M 合并或拆分按原子操作处理：必须同时启用两侧对应类型，否则整个操作保留在当前报告中。
- 固化前展示两侧差异，再以可恢复的三文件事务写入文档 A、文档 B 和更新后的报告。
- 已固化效果进入新正文与新 `ops` 基线，并从当前 `repair_log` 消失；其来源和认可留在 `history`，不再伪装成新基线的当前操作。未固化操作通过与普通重新对齐相同的关系协调器保留，不再维护固化专用的报告迁移算法，也不生成第二份位置状态。
- 重对齐后，两侧内容完全相同且在新旧关系中均唯一的关系继承旧 ID；改变边界或内容的关系获得从未使用的新 ID，不能仅凭新位置继承身份。
- `anomaly_diagnostics` 是对齐时冻结的关系级事实：非 `1:1`、语言杂糅和低分连同当次低分参数写入报告。之后调整 GUI 阈值只影响下一次重新对齐，不实时改变旧报告的筛选、颜色或人工审阅完成度；旧报告缺少该字段时使用固定兼容默认值。
- 固化前的完整操作及实际应用范围归档到 `history`。AI 建议按关系 ID 分组；已处理或目标已变化的建议会清理，未受影响的待处理建议直接继承最终关系 ID。持久评分以 `(relation_id, sub)` 为内存键并按关系 ID 嵌套写入报告；旧 `snap_sub` 键只在载入边界转换一次。完整固化且已有当前评分的关系会把该评分提升为新基线；部分固化则失效重算。
- `flag` 与 `ok` 不改写正文。`flag` 在目标关系完全相同时重锚保留；独立 `ok` 只在新基线仍把该关系识别为异常时保留，干净关系的旧认可仅留在历史。用户 `ok` 是对当前结果的最终裁决，会淘汰同关系尚未采纳的 AI 建议；`flag` 只是要求关注，可以与建议共存。内容固化改变关系时，其待处理 AI 建议和派生评分一并失效。
- `[F]` 表示尚未闭合的审阅事项，与正文决定正交。人工、自动或 AI 的 merge/split/edit/delete/placeholder 都不会暗中解除它；正文变化只会使旧 `ok` 失效。只有显式 `ok`、“删除标记”，或携带 `resolved_flag_actions` 的原子审校决定会解除 `[F]`；后续再次 flag 则重新开启事项。该规则按动作语义统一执行，不按动作来源增加分支。
- 跨关系 merge/edit 必须选择连续关系；非连续选择仍可复制、标记、删除或批量 AI 分析，但会在工具栏和右键菜单中禁用可能破坏单调顺序的正文动作。选择门控由服务层投影，GUI 不另存一套规则。
- 备份职责由 Git、文件历史或调用方承担，Dualign 不再生成 `.bak`。

## 阅读器兼容制品

逐行阅读器仍可消费等长的两份 Markdown，但它们不是数据源。构建时调用 `materialize_reader_rows()`，从源文档和报告在临时目录中重放并生成，构建完成立即删除。这样既保留现有阅读器兼容性，也避免长期维护 `repaired/` 副本。

## 明确移除的概念

- 不再隐式导出修订后的 Markdown；
- 不再维护 `repaired/`、`.bak` 或文件置换式“晋升”流程；
- 不用 YAML 复制 JSON 工作状态；
- 不提供旧报告格式迁移；
- 不把恢复文件与正式对齐数据拆成两套相互同步的权威状态。

## 数据流

```text
文档 A + 文档 B
       │
       ├── 对齐 ──> report.json
       │                 │
       │          校订 / AI / 人工审核
       │                 │
       │          原子保存 report.json
       │                 │
       ├── 按类型固化 <────┘
       │
       └── 阅读器构建：临时物化等行 Markdown ──> 静态站点
```
