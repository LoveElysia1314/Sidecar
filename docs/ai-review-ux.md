# AI 审校运行可视化设计

状态：设计方案，尚未实施 GUI 变更
更新日期：2026-08-27

## 问题

AI 审校已在工作线程运行，不会阻塞 Qt 事件循环，但用户在一次模型响应返回前只能看到状态栏中的“AI 校订中”。现有事件链还存在两处断层：

- 工作线程构造拟修复和审校区域时没有可见事件；
- Agent 发出 `llm_call` 后同步等待完整响应，GUI 又只把 `llm_call/tool_start` 写入 DEBUG；
- 区域工具返回的 `resolved_regions/total_regions` 没有投影到界面；
- GUI 仍监听旧的 `review_done`，而生产区域工具只发出 `tool_result`。

因此问题主要是缺少稳定的语义进度协议，而不是缺少一个文本输出框。

## 当前界面的职责分析

现有界面把三种不同生命周期的信息放得较近，容易让用户误以为它们是同一种“AI 状态”：

1. **运行状态**：本次调用正在准备、等待模型、执行工具或保存；结束后即失效。
2. **建议状态**：待处理、已应用、已拒绝；属于底部 AI 建议列表，可跨会话保存。
3. **服务状态**：底栏“大语言模型”的圆点只表示配置/连接可用，不表示正在审校，也不表示文档已经审校。

可视化应明确遵循这三个层次。尤其不新增常驻的“AI 已审校”标签：一次运行完成不是稳定的文档属性，正文或提示词变化后其含义也不可靠。持久结果继续由建议数量、建议状态和来源标记表达。

## 设计原则

1. 主界面显示用户可以理解和验证的审校进度，不显示隐藏推理、不完整 JSON 或逐 token 噪声。
2. 模型推理期间没有可信百分比，使用不确定进度；区域工具完成后才显示准确的 `x/y`。
3. 进度协议独立于模型供应商和工具名称。流式传输是底层能力，不成为 GUI 数据模型。
4. 界面保持非模态：运行时可以阅读正文和已有建议，但禁止重复启动或修改本轮输入快照。
5. 一个 `review_region` 是一个用户可感知的决定；附属的标记解除不显示成第二条建议。

## 推荐界面

首选位置是在左侧“AI 审校”组底部增加一条使用 Qt 原生控件的全宽活动条。这里紧邻“审校本条/审校本章”启动入口，用户不必在主表、底部建议栏和运行日志之间寻找反馈：

```text
⟳ 正在等待模型 · 00:18
━━━━━━━━━━━━━━━━━━━━  不确定进度

✓ 已处理区域 2/6 · 区域 R3 已生成编辑建议
━━━━━━━━────────────  2/6
```

活动栏包含：

- 阶段文字：准备拟修复、构造区域、等待模型、执行决定、保存建议；
- 已用时间；
- 不确定或 `已处理区域 x/y` 进度条；
- 最近一项经过整理的结果，例如“关系 21：重新分段”；
- 可选“详情”，打开既有日志信息，不在主界面铺陈调用参数。

活动条在空闲时隐藏；成功结束后短暂保留摘要，然后收起。这样不会永久增加左侧面板高度。等待模型时使用不确定进度，只有区域决定落地后才切换为 `x/y`，计时始终真实递增。

底部 AI 建议列表仍只承载持久结果；运行日志承载详细诊断；窗口状态栏只镜像一句简短状态。不要把逐 token 文本放进建议列表，也不要使用模态进度对话框，否则用户不能继续阅读正文和已完成建议。

### 组件精简建议

| 现有组件 | 判断 | 建议 |
| --- | --- | --- |
| “审校本条” | 保留 | 与批量入口配对，名称明确。 |
| “一键审校” | 改名 | 改为“审校本章”，直接说明范围，避免“一键”营销式表述。 |
| “一键应用” | 保留并改名 | 改为“全部应用”，它与单条“应用”分别代表批量和单条操作。 |
| “清除建议” | 降级 | 移到建议列表的更多菜单或右键菜单；它是低频、破坏性的维护动作，不应占主操作位。 |
| “上一建议/下一建议” | 后续迁移 | 与建议列表的点击导航职责重复；若仍需支持列表折叠时导航，应移到建议列表标题行或仅保留快捷键。 |
| “应用/拒绝/撤销” | 保留 | 它们是当前建议的核心人工决定，应该与建议焦点保持视觉关联。 |
| “大语言模型”圆点 | 保留但澄清 | 只表达服务可用性；tooltip 写明“服务可用性”，不拿它充当运行进度。 |
| `💡 待处理/总数` | 保留 | 这是持久建议状态，适合留在建议列表标题行。可去掉灯泡以减少装饰。 |
| 状态栏“AI 校订完成” | 短暂反馈 | 不作为文档的常驻状态；完成后由建议计数承接结果。 |

第一阶段不必立即搬动按钮。最小且协调的落地方式是先加入按需出现的活动条、修正运行期门控，并把“一键审校”改为“审校本章”；低频按钮和导航迁移可以在活动条验证后单独完成，避免一次重排破坏用户肌肉记忆。

## 语义事件协议

Agent 服务层应发出稳定的领域事件，Qt 适配层只负责转发：

```text
run_started(total_regions)
phase_changed(preparing | waiting_model | applying | saving)
region_resolved(region_id, relation_ids, decision, completed, total, summary)
usage_updated(tokens)
run_finished(status)
run_failed(message)
```

`region_resolved` 在工具执行器接受一个区域决定后产生，并携带该次新增动作，而不是让 GUI 解析 `tool_result` JSON。它同时替代已经失效的 `review_done` 路径，使建议可以在一轮中的每个区域完成后进入建议表。

计时数据应与语义事件正交：`llm_response` 和 `tool_result` 可以携带本阶段耗时，`run_finished` 携带总耗时。日志保留模型等待、工具执行和其余准备/调度三项分解；GUI 默认只显示总耗时，详情中再展示分解，避免增加认知负担。

## 控件与取消

运行期间应禁用再次启动 AI、切换策略及会改变审校快照的正文操作；表格导航、阅读和查看既有建议保持可用。当前按钮门控没有覆盖“审校本条”和“一键审校”，实施时必须一并修正，以避免并行启动两个 Agent。

当前后端在 watchdog 线程中等待非流式 HTTP 调用，`QThread.requestInterruption()` 不能终止请求。因此第一阶段不提供伪取消按钮。真正取消需要后端流式连接或可传播的取消令牌，并在关闭连接后由 Agent 发出确定的终止状态。

## 实施顺序

### 第一阶段：最高收益

- 增加上述语义事件；
- 增加原生活动栏、计时和不确定/确定进度切换；
- 消费区域完成事件并增量显示建议；
- 修正运行期间的控件门控。

这一阶段不要求模型 API 流式化，改动集中在 Agent/Qt 之间的协议与视图状态。

### 第二阶段：可选增强

- 后端支持流式 Responses 事件和协作式取消；
- 用流事件缩短首次反馈时间；
- 仅把完整工具调用转换为语义状态，原始输出保留在调试日志。

不建议为了制造进度感而把每个区域强制拆成独立模型请求。这会增加费用和延迟，并削弱错位、重复和 `[F]` 分歧区所需的跨区域上下文。超大章节如有需要，应按上下文边界自适应分批，而不是固定逐关系调用。

## 非目标

- 不展示模型隐藏推理；
- 不展示不断变化的函数参数；
- 不伪造推理百分比；
- 本设计文档本轮不实施 GUI 改动。
